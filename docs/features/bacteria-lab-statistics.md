# 菌落实验室使用统计

## 需求与完成标准

2026-10-02 新增独立菌落实验室统计页。首版支持使用频率、关卡挑战结果、机会购买和可观察连续失败；后续调整以实际数据记录能力为依据。

- 沿用现有页签、独立并发加载、当前页每60秒刷新、主题和响应式版面。
- 最近7个自然日包含今天和此前6天，按看板时区 Asia/Tokyo 展示，今天截至查询时间。
- 展示活跃医院、成功/失败结算、结算成功率、每医院活跃日结算次数、每日和小时分布、活跃天数分布。
- 展示实际机会购买医院与次数、元宝消耗、期内复购、活跃医院中的实际购买占比、机会耗尽请求。
- 展示通关前连续失败均值、最大值和分布，并标注有效样本数。
- 展示当前最高通关分布、近7日医院使用排行 Top 50、机会购买医院 Top 50、关卡通关与重玩奖励记录。
- 新接口 /api/bacteria-lab-stats 继承 Firebase 登录和统计节点 Bearer 鉴权；统计 SQL 只在只读备份节点执行。
- 无数据时分母为零的指标显示占位；数据源失败时显示错误并清空图表，禁止显示为真实零值。
- 单元测试、真实副本查询、浏览器功能、Console、网络、响应式和截图检查通过后提交。用户追加要求：完成后直接发布 ccnode 运行环境，先发布依赖统计节点。

## 指标定义

| 指标 | 定义 |
| --- | --- |
| 活跃医院 | 期内有成功或失败结算日志的去重医院 |
| 结算次数 | 精确匹配实验机会成功/失败日志，排除请求失败和未结算尝试 |
| 成功率 | 成功结算 / 全部结算，包含重玩 |
| 每活跃日结算 | 总结算 / 各医院活跃自然日数之和 |
| 机会购买 | 精确匹配补满服务元宝流水原因且 old_value > new_value；一条实际扣款为一次购买 |
| 期内复购 | 期内至少两次实际购买的去重医院 |
| 活跃购买占比 | 期内同时活跃及购买的医院 / 期内活跃医院；无结算买家单独保留在购买榜 |
| 机会耗尽 | 精确匹配机会耗尽拒绝请求，重复请求分别计数 |
| 连续失败样本 | 同一医院两次观察到的成功结算之间的失败数；排除窗口内首次成功和尾段未成功失败；日志按时间和ID排序 |
| 当前进度 | 玩家状态 highest_cleared_level，仅纳入 active_attempt_id 或 last_settled_attempt_id 非空的医院 |
| 关卡奖励 | 系统日志精确匹配样本通关奖励或重玩奖励前缀，按关卡及医院统计 |

## 数据来源与限制

- t_bacteria_lab_player_state：当前状态。建立状态可能只代表查看页面，不能当作开始或完成挑战；不以 update_time 推算玩法活跃。
- t_log_right_bottom：成功、失败及耗尽拒绝日志，游戏代码保留7天。源时间为无时区UTC，查询边界使用看板自然日转UTC。
- t_log_yuanbao：元宝扣款。匹配当前原因“菌落清除室补满实验机会”和历史正式商店原因“商店购买: 菌落清除室实验机会补满 x 1”。历史原因纳入同一已发生业务流水统计，不改变游戏行为。
- t_log_system：通关和重玩奖励，源保留15天，本页只读取同一7日窗口。
- t_hospitals：名称与院长，使用实际字段 hospital_name。返回内容转义，尝试UUID不返回前端。
- 单关失败没有关卡号、完整尝试历史与尝试编号。单关首次通关重试和单关成功率不能还原；连续失败样本可能跨关卡，包含重玩。
- 补满到5次是一次服务，实际新增机会数随购买前余额变化；流水不能直接推算新增机会或现金收入。
- 购买意向、商店浏览、直接退出和完整开始次数没有足够日志，不能以耗尽请求替代购买意向。
- 7日窗口外的行为不展示为零，也不提供长期频率或留存结论。未结算状态可能已离线，不能当作当前在线人数。
- 不新增游戏写入、埋点、数据库结构、迁移或采样机制。后续若要求精确单关重试与长期留存，需要单独扩展游戏事件记录及发布验收。
